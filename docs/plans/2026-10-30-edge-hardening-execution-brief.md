## 0. 开工前置（一次性，主 Agent 自己核对）

1. tsink_fork 工作树必须干净（`git status` 无输出）——前置已由人类提交；若仍有脏文件且不属于
   本计划，立即停止并按 §5-d 报告，**不得**把既有脏文件卷进本计划的提交。
2. 通读顺序：权威计划全文 → 本简报 → `~/.zcode/AGENTS.md` → `/root/myprojects/webhmi/AGENTS.md`
   → tsink 仓 `docs/`（storage-engine / compaction / architecture 现状小节，改文档要用）。
3. 若环境提供 `rust` / `test-driven-development` / `executing-plans` 技能，先加载再动手。

## 1. 编排模型（严格串行）

- 主 Agent = 编排 + 复核，**不写功能代码**；唯一例外：复核中发现 ≤10 行的明确小错
  （typo / 漏导入 / clippy）可直接修，并在复核记录注明。
- 每个任务（计划中的 Wx-Ty 粒度）派 1 个 subagent（general-purpose，`run_in_background: false`
  同步取回结果），同一时刻只允许 1 个 subagent 在跑。只读侦察（读代码/读文档）主 Agent 自己做。
- 顺序与计划「执行顺序」一致：W1(T1→T3) → W2(T1→T3) → W3(T1→T5) → W4(T0→T5)；
  W4-T0 必须先于 W4-T1。任务被阻塞按 §5 处理，不得乱序跳进依赖它的后续任务。
- W1-T4 计划已标注「可选」，默认不做，终报注明。

### subagent prompt 模板（每份必须自包含——subagent 看不到会话上下文）

1. 任务 ID + 目标一句话；
2. 权威计划路径 + 该任务小节**原文逐字粘贴**（含红/绿判据与 file:line 锚点）；
3. 仓库根：`/root/myprojects/webhmi/tsink_fork`；
4. 边界：只准改哪些文件/模块；禁改清单（生产服务、rs-iot、`_oss-refs/`、计划与简报本身）；
5. TDD 步骤（§2）与验证命令逐条给出；
6. 返回格式：改动文件清单 / 红证据（命令 + 真实输出摘录）/ 绿证据 / `cargo test --lib` 结果 /
   未解决问题列表。返回缺证据即打回。

## 2. TDD 纪律（每个任务同样流程）

1. **红**：先写测试，运行精确命令，拿真实输出证明「以预期方式失败」（断言红，或计划明文
   声明的编译红）——环境/编译事故不算红；
2. **绿**：最小实现转绿；**禁止为转绿降低断言**（计划 W1 明文）；
3. **收口**：`cargo test -p tsink --lib`；过滤单测时用 `-- --exact` 并核对输出里的测试二进制与
   用例数（曾发生过滤串命中另一个 19 用例二进制的事故）；
4. **W 边界**（每个 W 的最后一个任务后）全量门禁：`cargo test -p tsink` +
   `cargo fmt --all -- --check` + `cargo clippy --lib --all-targets`
   （已知：`fetch_update` 已弃用，用 `try_update`）；
5. 已知基线红（允许红、不算回归、也不要去修）：`retention_policy::compute_only_storage_suppresses*`
   （root 下 chmod 000 无效，见 workspace AGENTS.md #5）。除它以外任何红都是回归。

## 3. 复核清单（主 Agent 在 subagent 返回后、提交前逐项过）

1. **证据真实性**：亲自重跑该任务的新增测试（精确过滤）+ `cargo test -p tsink --lib`，比对输出；
2. **diff 精准性**：逐文件看 diff（per-task 提交后用 `git show`）——无计划外改动、无意外删除整段
   （曾发生 Edit 误删相邻函数开头的事故，重点看被改文件的函数边界完整性）；
3. **计划符合度**：任务小节的 file:line 锚点与语义逐条对照；任何偏离必须在「实施状态」表备注；
4. fmt / clippy 0 新增告警；
5. 计划文档「实施状态」表更新（⏳→✅ + commit 短哈希 + 一句话证据）；
6. 提交信息符合仓内 `git log` 风格，不带任何 AI 署名尾注。

## 4. 提交与进度

- 默认策略（人类已批准）：**每任务复核通过后单独一笔提交**，只 add 本任务实际改动的文件；
  **禁止 push**（push 由人类决定）。
- 进度唯一权威 = 计划文档「实施状态」表 + git log。会话内另维护简短决策记录
  （每条：任务 ID、决策、理由，两行以内），最终附在汇报里。

## 5. 失败与自主决策

- **打回**：复核不过 → 带具体缺陷描述重派该任务的新 subagent；每任务最多打回 2 次；
  仍不过 → 实施状态标 🔴 + 阻塞原因，仅继续不依赖它的后续任务。
- **自主决策范围**：可逆实现细节（命名、测试摆放、内部结构），必须记入决策记录。
- **禁止即停**（停下写交接报告，等人类）：
  a) 需要破坏性/不可逆操作（删数据、改仓外生产文件——除 §6 明确授权的 W3-T5 部署）；
  b) 发现计划自相矛盾或锚点失效到必须改架构才能继续；
  c) ≥3 个任务阻塞；
  d) W3-T5 部署后健康检查不过且回滚也失败。
- **回滚预案**（W3-T5 前必做）：备份当前 rs-iot release 二进制（cp 加日期后缀）；重启后
  `GET /api/v1/health` 不过 → 恢复备份二进制 → 再 restart → 仍不过即触发 d。

## 8. 断点续跑（会话中断/压缩后）

若有未提交改动属于中断中的任务：先跑该任务的测试评估可否收口，可则走完复核再提交；
不可则记录后重派 subagent（**不要盲目 git reset**）。
